Глава 11: Чего следует избегать

Чего следует избегать

Perl — гибкий язык. Вы можете писать программы так, как вам нравится: креативно, поддерживаемо, запутанно или странно. Хорошие программисты пишут код, который удобно поддерживать, но Perl сам не определяет, что именно считать поддерживаемым.

Perl не идеален. Некоторые его возможности трудно использовать правильно. Другие выглядят многообещающе, но работают не лучшим образом. Есть и странные граничные случаи. Зная, чего следует избегать — и когда, — вы сможете писать надёжный код, способный выдержать испытание временем и реальными пользователями.

Barewords

Парсер Perl распознаёт встроенные функции и операторы языка. Он использует сигилы для определения переменных и другую пунктуацию для вызова функций и методов. Однако иногда парсеру приходится угадывать, что вы имели в виду, особенно при использовании bareword — идентификатора без сигила или другой синтаксической подсказки.

Хорошее использование barewords

Ключи хеша
Ключи хеша в Perl обычно однозначны, так как парсер понимает их как строки:

my $value = $items{shift}; # ключ — литерал 'shift'
my $value = $items{shift @_}; # ключ — результат функции shift
my $value = $items{myshift(@_)}; # ключ — результат своей функции
my $value = $items{+shift}; # унарный плюс заставляет интерпретировать shift как встроенную функцию

Имена пакетов
Имена пакетов тоже являются barewords. Если вы придерживаетесь соглашения, что имена пакетов с заглавной буквы, а функции — нет, то редко будете сталкиваться с проблемами. Чтобы явно указать парсеру, что это пакет, можно:

Package->method; # скорее всего метод класса
Package::->method; # точно метод класса
'Package'->method; # строка и метод
my $q = Plack::Request::->new;
my $q = 'Plack::Request'->new;

Хотя в реальном коде так почти никто не пишет, важно уметь это читать.

Именованные кодовые блоки
Специальные блоки AUTOLOAD, BEGIN, CHECK, DESTROY, END, INIT и UNITCHECK тоже являются barewords и могут объявляться без ключевого слова sub:

package Monkey::Butler;
BEGIN { initialize_simians(__PACKAGE__) }
sub AUTOLOAD { ... }

Константы
Константы, объявленные через constant, также можно использовать как barewords:

use constant NAME => 'Bucky';
use constant PASSWORD => '|38fish!head74|';

return unless $name eq NAME && $pass eq PASSWORD;

Но такие константы не интерполируются в двойных кавычках.

Небезопасное использование barewords

Значения хеша
В старом коде можно встретить незаключённые в кавычки значения хеша:

my %parents = (
    mother => Annette,
    father => Floyd,
);

Если функций Annette() и Floyd() нет, Perl интерпретирует их как строки. strict 'subs' в этом случае выдаст ошибку.

Вызовы функций
Без strict 'subs' функции могут вызываться как barewords. Добавление скобок исправит проблему. Чтобы понять, как именно Perl интерпретирует код, используйте:

perl -MO=Deparse,-p your_script.pl

Файловые дескрипторы
До появления лексических файловых дескрипторов все файловые и директорные дескрипторы были barewords. Сегодня стоит переписывать такой код, кроме специальных STDIN, STDOUT и STDERR.

Функции сортировки
В sort можно указать имя функции как bareword:

my @sorted = sort compare_lengths @unsorted;

Или явно использовать ссылку на функцию:

my $comparison = \&compare_lengths;
my @sorted = sort $comparison @unsorted;

Но нельзя напрямую написать:

my @sorted = sort \&compare_lengths @unsorted; # не сработает

Лучше использовать блочный вариант sort там, где это возможно.

Косвенные объекты (Indirect Objects)

Perl не чисто объектно-ориентированный язык. В Perl нет оператора new — конструктор это просто метод, который возвращает объект. Старые учебники по Perl иногда советуют стиль C++/Java:

my $q = new Alces; # НЕ ИСПОЛЬЗУЙТЕ

Вместо очевидного варианта:

my $q = Alces->new;

Косвенные вызовы выглядят красиво, но вызывают неоднозначности парсинга.

Bareword в косвенных вызовах

Когда имя метода — bareword, парсер применяет эвристики для его интерпретации. Они работают почти всегда, но в случае ошибки код становится трудно дебажить, особенно если передаются аргументы:

my $obj = new Class(arg => $value); # НЕ ИСПОЛЬЗУЙТЕ

Ошибки возможны из-за совпадения имён пакетов, функций или прототипов.

Ограничения косвенного синтаксиса

Ещё одна проблема: косвенный синтаксис ожидает одиночное скалярное выражение для объекта. Например, печать в файловый дескриптор в хеше:

# НЕ РАБОТАЕТ
say $config->{output} 'Сообщение';

Perl попытается вызвать метод say у объекта $config. Правильный способ:

say {$config->{output}} 'Сообщение';

Альтернативы косвенному синтаксису

Прямой вызов конструктора не страдает от проблем неоднозначности. Чтобы создать объект, вызывайте метод конструктора напрямую через имя класса:

my $q = Plack::Request->new;
my $obj = Class->new( arg => $value );

Однако остаётся проблема с bareword: если в пространстве имён Plack существует функция с именем Request, Perl интерпретирует вызов так:

sub Plack::Request;

# Вы написали
Plack::Request->new;

# А Perl увидел
my $q = Plack::Request()->new;

Разрешайте такую неоднозначность привычными способами (см. "Имена пакетов — bareword").

В ограниченных случаях, связанных с файловыми дескрипторами, можно использовать косвенный синтаксис, если обернуть нужный объект в фигурные скобки. Методы можно вызывать и на лексических файловых дескрипторах, хотя почти никто так не делает для print и say.

Модуль Perl::Critic::Policy::Dynamic::NoIndirect для Perl::Critic позволяет находить косвенные вызовы в коде. Модуль indirect может запретить их использование на этапе выполнения:

# Выдавать предупреждения
no indirect;

# Вызывать исключения
no indirect ':fatal';

Прототипы

Прототип — это метаинформация, прикреплённая к функции или переменной. Прототип меняет поведение парсера Perl при разборе вызова функции.

Прототипы позволяют создавать собственные функции, которые ведут себя как встроенные. Например, встроенная push принимает массив и список. Обычно Perl "сплющивает" аргументы в один список, но для push этого не происходит, так как парсер понимает, что нужно сохранить ссылку на массив.

Прототипы указываются в объявлении функции:

sub foo (&@);
sub bar ($$) { ... }
my $baz = sub (&&) { ... };

Прототипы должны совпадать в предварительных объявлениях и определениях функций. Иначе Perl выдаст предупреждение. Хотя можно опустить прототип в предварительном объявлении, реального смысла в этом нет.

Встроенная функция prototype возвращает строку с прототипом переданной функции. Чтобы получить прототип встроенной функции, укажите имя через CORE:::

$ perl -E "say prototype 'CORE::push';"  # выведет: \@@
$ perl -E "say prototype 'CORE::keys';"
$ perl -E "say prototype 'CORE::open';"

Если у встроенной функции нет прототипа, prototype вернет undef:

say prototype 'CORE::system' // 'undef'; # undef
say prototype 'CORE::prototype' // 'undef'; # undef

Пример для push:

$ perl -E "say prototype 'CORE::push';"
\@@

Здесь @ означает список, а обратная косая черта (\) — передачу ссылки на массив. Таким образом, push принимает ссылку на массив и список значений. Можно написать аналогичный mypush:

sub mypush (\@@) {
    my ($array, @rest) = @_;
    push @$array, @rest;
}

Другие символы в прототипах:

  • $ — скаляр;
  • % — хеш (чаще всего ссылка на хеш);
  • & — блок кода.

Подробнее см. perldoc perlsub.

Проблемы с прототипами

Прототипы меняют как Perl парсит код, так и как интерпретируются аргументы функций. Хотя они напоминают сигнатуры функций из других языков, на самом деле это совершенно разные вещи. Прототипы не описывают количество и типы аргументов и не сопоставляют их с именами параметров.

Приведение аргументов через прототипы происходит тонко, например, при принудительном переводе в скалярный контекст:

sub numeric_equality($$) {
    my ($left, $right) = @_;
    return $left == $right;
}

my @nums = 1 .. 10;
say 'Они равны!' if numeric_equality @nums, 10;

...но это работает только для простых выражений:

sub mypush(\@@);

# Ошибка компиляции: несовпадение прототипа
mypush(my $elems = [], 1 .. 20);

Чтобы разобраться с такой ошибкой, пользователь mypush должен знать о существовании прототипа и его особенностях. Это создаёт высокую когнитивную нагрузку, а сообщения об ошибках с прототипами могут быть очень запутанными.

Хорошее использование прототипов

У прототипов всё же есть несколько достойных применений, перевешивающих их недостатки. Например, можно использовать прототип для переопределения встроенной функции Perl. Сначала проверьте прототип встроенной функции в тестовой программе. Затем используйте прагму subs, чтобы сообщить Perl о намерении переопределить встроенную функцию. И наконец, объявите функцию с правильным прототипом:

use subs 'push';
sub push (\@@) { ... }

Имейте в виду: pragma subs действует до конца файла, независимо от лексической области.

Прототипы также можно использовать для определения констант времени компиляции. Если Perl видит функцию с пустым прототипом и её тело — это константное выражение, все вызовы такой функции оптимизируются в подстановку константы:

sub PI () { 4 * atan2(1, 1) }

В дальнейшем код будет использовать предвычисленное значение pi вместо вызова функции PI().

Прагма constant в Perl упрощает создание констант. Модуль CPAN Const::Fast позволяет создавать неизменяемые скаляры, которые можно интерполировать в строки.

Ещё разумное использование прототипов — работа с анонимными функциями как с блоками. Модуль Test::Exception применяет это для удобного API с отложенным вычислением:

use Test::More;
use Test::Exception;

throws_ok
    { my $unobject; $unobject->yoink }
    qr/Can't call method "yoink" on an undefined/,
    'Метод на неопределённом объекте должен упасть';

done_testing();

Функция throws_ok имеет прототип &$;$: первый аргумент — анонимная функция, второй — скаляр, третий — необязательный.

Обратите внимание: после блока нет запятой. Это особенность парсера Perl — он ожидает пробел после блока, а не оператор запятой. Чтобы избежать этой особенности, можно явно обернуть блок в sub { }:

use Test::More;
use Test::Exception;

throws_ok(
    sub { my $unobject; $unobject->yoink() },
    qr/Can't call method "yoink" on an undefined/,
    'Метод на неопределённом объекте должен упасть'
);

done_testing();

Модуль Test::Fatal предлагает похожий подход с меньшими двусмысленностями.

Бен Тилли предложил ещё один хороший пример использования прототипов — для определения функции сортировки:

sub length_sort ($$) {
    my ($left, $right) = @_;
    return length($left) <=> length($right);
}

my @sorted = sort length_sort @unsorted;

Прототип $$ заставляет Perl передавать пары элементов в @_. Документация sort упоминает, что это немного медленнее, чем использование глобальных $a и $b, но лексические переменные часто компенсируют эту разницу.

Эквивалентность метода и функции

Объектная система Perl минималистична: класс — это пакет, а Perl не различает методы и функции в пакете. Встроенная конструкция sub объявляет и функции, и методы.

Perl спокойно вызывает функцию как метод и наоборот. Вы можете вызывать метод как функцию (с явной передачей инвоканта), экспортировать его или обращаться по ссылке.

Со стороны вызывающего кода

Рассмотрим класс с несколькими методами:

package Order {
    use List::Util 'sum';
    sub calculate_price {
        my $self = shift;
        return sum(0, $self->get_items);
    }
    ...
}

Имея объект $o класса Order, можно вызвать метод так:

my $price = $o->calculate_price;

или так (НЕ рекомендуется):

my $price = Order::calculate_price($o);

Хотя результат может быть одинаковым, второй вариант нарушает инкапсуляцию объекта и обходит механизм поиска метода.

Если $o — это подкласс или роль, переопределяющая calculate_price(), вызов через Order::calculate_price() приведёт к неправильному результату.

Если изменить структуру наследования или использовать AUTOLOAD(), такой вызов может легко сломаться.

Perl допускает прямой вызов ссылки на метод, полученной через can():

my $meth_ref = $o->can('apply_discount');

Тогда возможны два варианта:

$o->apply_discount if $o->can('apply_discount');

или

if (my $meth_ref = $o->can('apply_discount')) {
    $o->$meth_ref();
}

Также можно вызвать метод по имени через переменную:

my $name = 'apply_discount';
$o->$name();

Минус вызова через ссылку: если структура программы изменится после получения ссылки, ссылка может устареть. Лучше ограничивать область жизни таких ссылок.

Со стороны вызываемой функции

Поскольку можно вызывать функции как методы и наоборот, можно написать функцию, которая допускает оба варианта вызова.

Например, в модуле CGI используются "двуличные" функции, которые через эвристики определяют, является ли первый аргумент инвокантом. Это вызывает сложности:

  • трудно предсказать, какие инвоканты допустимы;
  • труднее документировать API;
  • легко допустить ошибку при переходе между процедурным и объектным интерфейсом.

Если необходимо поддерживать и процедурный, и объектный интерфейс, лучше создавать для них отдельные API.

Автоматическое разыменование

Perl может автоматически разыменовывать некоторые ссылки за вас. Имея ссылку на массив в $arrayref, вы можете написать:

push $arrayref, qw( list of values );

Аналогично, если выражение возвращает ссылку на массив:

push $houses{$location}[$closets], \@new_shoes;

Эксперимент с автодереференсом

Начиная с Perl 5.18, для включения этой функции требуется:

use experimental 'autoderef';

Это уже должно быть сигналом к осторожности.

То же самое касается операторов массивов pop, shift, unshift, splice, keys, values, each и операторов хеша keys, values, each. Если ссылка неправильного типа, Perl выбросит исключение.

Хотя это кажется опасным, на самом деле поведение такое же, как при явном разыменовании:

my $ref = sub { ... };
# выбросит исключение
push $ref, qw( list of values );

# тоже выбросит исключение
push @$ref, qw( list of values );

Однако у автоматического разыменования есть две проблемы:

  1. Оно работает только с обычными ссылками. Если ссылка благословлена в объект, завязана (tied) или перегружена — будет ошибка во время выполнения.
  2. Операторы each, keys и values работают и для массивов, и для хешей. Нельзя по коду:
my @items = each $ref;

понять, что именно находится в @items — пары ключ/значение или индекс/значение.

Эти недостатки не делают автодереференс бесполезным, но усложняют понимание кода.

tie

Если перегрузка (см. "Перегрузка", стр. 231) позволяет настраивать поведение объектов, то механизм tie позволяет настраивать поведение примитивных переменных (скаляров, массивов, хешей, файловых дескрипторов).

Любая операция с завязанной переменной фактически вызывает определённый метод объекта.

Например, встроенная функция tie позволяет модулю Tie::File работать с файлами как с массивами строк, используя push, pop и shift.

Класс, к которому привязывается переменная, должен реализовать стандартный интерфейс для типа данных. См. perldoc perltie для обзора и модули Tie::StdScalar, Tie::StdArray, Tie::StdHash для подробностей.

Когда имена классов и пакетов конфликтуют

Дополнительную путаницу вносит то, что Tie::Scalar, Tie::Array и Tie::Hash описывают интерфейсы, а Tie::StdScalar, Tie::StdArray и Tie::StdHash — их стандартные реализации.

Привязка переменных

Чтобы привязать переменную:

use Tie::File;
tie my @file, 'Tie::File', @args;

Первый аргумент — переменная. Второй — имя класса. @args — необязательные параметры, например, имя файла для Tie::File.

Функции привязки похожи на конструкторы: TIESCALAR, TIEARRAY, TIEHASH или TIEHANDLE. Они возвращают объект для управления переменной. Функции tie и tied возвращают объект (обычно tied используется в булевом контексте).

Реализация привязанных переменных

Чтобы реализовать класс для привязки:

  • наследуйтесь от Tie::StdScalar;
  • переопределите нужные методы (например, FETCH и STORE для скаляров).

Пример класса, логирующего чтение и запись скаляра:

package Tie::Scalar::Logged {
    use Tie::Scalar;
    use parent -norequire => 'Tie::StdScalar';

    sub STORE {
        my ($self, $value) = @_;
        Logger->log("Сохраняем <$value> (было [$$self])", 1);
        $$self = $value;
    }

    sub FETCH {
        my $self = shift;
        Logger->log("Читаем <$$self>", 1);
        return $$self;
    }
}

Предполагается, что метод log() класса Logger принимает сообщение и количество кадров стека для отчёта о местоположении.

В методах STORE и FETCH переменная $self — это благословенная ссылка на скаляр. Присваивание меняет значение, чтение возвращает значение.

Аналогично работают Tie::StdArray и Tie::StdHash для массивов и хешей соответственно. Подробнее — в perldoc perltie.

Разве tie — это не весело?

Опция -norequire для parent предотвращает попытку загрузить отдельный файл для Tie::StdScalar, поскольку он определён в файле Tie/Scalar.pm без отдельного .pm-файла. Да, это всё действительно так. Весело, правда?

Когда использовать привязанные переменные

Привязанные переменные могут казаться интересной возможностью для хитрых решений, но они способны привести к запутанным интерфейсам. Если у вас нет веской причины делать объекты, ведущие себя как встроенные типы данных, избегайте создания своих привязок без серьёзной необходимости.

Кроме того, привязанные переменные работают гораздо медленнее, чем обычные встроенные типы.

Тем не менее, привязанные переменные могут быть полезны для отладки сложного кода (например, с использованием журнала чтений и записей скаляра) или для реализации невозможных задач (например, доступ к очень большим файлам без переполнения памяти). Однако использовать привязку как основной интерфейс объектов — плохая идея: адаптировать весь интерфейс под ограничения tie() слишком сложно и неудобно.

И последнее предупреждение: многие сторонние библиотеки (случайно или намеренно) не поддерживают привязанные переменные. Это печально, но факт: сторонний код иногда работает быстро и упрощённо, не учитывая возможности привязки, и вы не всегда сможете это исправить.

Следующие шаги с Perl

Perl не идеален, но он гибок — потому что не существует одной идеальной конфигурации для всех программистов и для всех целей. Некоторые полезные поведения доступны в составе стандартной библиотеки. Ещё больше доступно на CPAN. Эффективные программисты Perl используют все доступные им возможности.

Полезные стандартные модули

Проектирование языка Perl всегда стремилось сочетать практичность с расширяемостью, но невозможно было предсказать будущее ни в 1994 году, ни в 2015-м.

Perl 5 расширил язык и сделал возможным появление CPAN, при этом сохранив обратную совместимость с кодом Perl 1, написанным ещё в 1987 году.

Лучший код на Perl в 2015 году сильно отличается от лучшего кода 1994 или 1987 годов, и часть этой эволюции заслуга стандартной библиотеки.

Прагма strict

Прагма strict позволяет запретить (или снова разрешить) использование некоторых мощных возможностей языка, потенциально приводящих к ошибкам.

strict запрещает:

  • символические ссылки,
  • использование переменных без явного объявления (лексическая область видимости),
  • использование необъявленных bareword-значений.

Хотя символические ссылки иногда нужны, их использование создаёт риск трудноуловимых ошибок или даже уязвимостей (например, возможность модификации приватных данных через ввод пользователя).

Требование объявления переменных помогает обнаруживать опечатки и правильно ограничивать область видимости переменных. Если все переменные имеют явные my или our объявления, намеренная область видимости становится очевидной.

strict действует в пределах лексических областей. См. perldoc strict для подробностей.

Прагма warnings

Прагма warnings управляет выводом различных классов предупреждений, например:

  • попытки привести undef к строке,
  • использование неправильного оператора для типов данных,
  • использование устаревших возможностей.

Наиболее полезные предупреждения сообщают, что Perl не понял ваш код однозначно и вынужден был делать предположения. Даже если Perl правильно угадал, явное уточнение вашего кода делает его более надёжным.

Прагма warnings тоже действует в пределах лексических областей. См. perldoc perllexwarn и perldoc warnings.

Как запросить больше помощи

Если вы используете warnings вместе с diagnostics, вы получите расширенные пояснения ко всем предупреждениям прямо из perldoc perldiag.

Это очень полезно при изучении Perl. Но убедитесь, что вы отключили diagnostics перед публикацией программы, чтобы не засорять логи или случайно не раскрыть отладочную информацию пользователям.

Прагма autodie

В Perl ответственность за обработку (или игнорирование) ошибок лежит на вас. Если забыть проверить возврат open(), можно попытаться читать из закрытого файлового дескриптора — или хуже, потерять данные при записи.

Прагма autodie меняет это поведение. Например:

use autodie;
open my $fh, '>', $file;

Если open() не удастся, будет выброшено исключение.

Так как выбрасывание исключения — это лучший способ обработки ошибок при системных вызовах, autodie позволяет избавиться от большого количества шаблонного кода и быть уверенным, что ни одна ошибка не останется незамеченной.

Предупреждение: autodie может оказаться "кувалдой вместо молотка"; если вам нужно проверять только несколько системных вызовов, можно ограничить импортируемые функции. См. perldoc autodie для подробностей.

Номера версий Perl

Если вы столкнулись с кодом на Perl, не зная его авторства и даты написания, сможете ли вы определить, для какой версии Perl он предназначен?

Если у вас есть опыт работы с Perl до и после версии 5.10, вы можете помнить, когда появились say и autodie. Иначе придётся угадывать, читать perldelta или использовать модуль CPAN::MinimumVersion.

Хотя не обязательно явно указывать минимально требуемую версию Perl, это помогает прояснить намерения автора. Например:

use 5.018;

Это задокументирует, что ваш код написан под Perl 5.18. Если позже выяснится, что он работает и на Perl 5.14, версию можно будет скорректировать.

Что дальше?

Хотя стандартная библиотека Perl обширна, она не охватывает всё. Многие лучшие модули доступны на CPAN. Мета-дистрибуция Task::Kensho собирает лучшие практики CPAN.

Когда вам нужно решить задачу, сначала ищите решения там.

Некоторые примеры:

  • Доступ к базам данных через SQL: DBI
  • Лёгкая встроенная БД: DBD::SQLite
  • Управление схемами БД: Sqitch
  • ORM для БД: DBIx::Class
  • Базовое веб-программирование: Plack
  • Полноценные веб-фреймворки: Mojolicious, Dancer или Catalyst
  • Обработка CSV-файлов: Text::CSV_XS (или Text::CSV)
  • Управление установкой модулей: Carton
  • Работа с числовыми данными: PDL
  • Работа с изображениями: Imager
  • Доступ к общим библиотекам: FFI::Platypus
  • Извлечение данных из XML: XML::Rabbit
  • Автоформатирование кода: Perl::Tidy
  • Анализ проблем кода: Perl::Critic

Следите за новыми релизами на CPAN — страница новых загрузок обновляется регулярно.

Мышление в стиле Perl

Как и в любом творческом процессе, изучение Perl никогда не заканчивается. То, что описано как "Modern Perl", — это лишь отражение текущих лучших практик. Инструменты и методы постоянно эволюционируют.

То, что кажется выдающимся в 2015–2016 годах, ещё даже не существовало пять лет назад. И идеи, которые изменят Perl в 2025 году, возможно, только зарождаются в чьей-то голове.

Теперь у вас есть шанс участвовать в формировании будущего Perl. Учитесь у мирового сообщества Perl, изучайте документацию стандартной библиотеки и CPAN, экспериментируйте и находите подходы, которые работают для вас.

Perl не идеален (хотя он постоянно улучшается с каждой версией). Он может быть таким чистым или хаотичным, каким вы захотите — всё зависит от решаемой задачи. Ваша ответственность — использовать его правильно.

Как сказал один мудрый человек: «Да будут ваши дела с Perl добрыми!»
