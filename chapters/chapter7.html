Глава 7: Объектно-ориентированное программирование

Объекты

Каждая крупная программа имеет несколько уровней проектирования: от конкретных деталей задачи до организации кода на верхнем уровне. Для управления этой сложностью нужны абстракция и инкапсуляция.

Функций бывает недостаточно. Один из популярных подходов — объектно-ориентированное программирование (ООП), где программы работают с объектами — уникальными сущностями с собственными данными.

Moose

Базовая объектная система Perl минимальна, но гибка. Для удобства используется Moose — полноценная объектная система, доступная через CPAN.

package Cat {
    use Moose;
}

Создание экземпляров класса:

my $brad = Cat->new;
my $jack = Cat->new;

Методы

Метод — это функция, связанная с классом. Первый аргумент метода — это $self (вызываемый объект или класс).

package Cat {
    use Moose;
    sub meow {
        my $self = shift;
        say 'Meow!';
    }
}

my $choco = Cat->new;
$choco->meow;

Методы, работающие с данными объекта, называются экземплярными. Конструкторы вроде new() — это методы класса.

Атрибуты

Атрибуты — это уникальные данные объекта. В Moose атрибуты объявляются через has:

package Cat {
    use Moose;
    has 'name', is => 'ro', isa => 'Str';
}

Создание объектов с параметрами:

my $cat = Cat->new( name => 'Tuxie' );
say "Created a cat for ", $cat->name;

Полная форма записи:

has 'name' => ( is => 'ro', isa => 'Str' );

Можно делать атрибуты доступными для записи с помощью rw:

package Cat {
    use Moose;
    has 'name', is => 'ro', isa => 'Str';
    has 'age', is => 'ro', isa => 'Int';
    has 'diet', is => 'rw';
}

my $fat = Cat->new(
    name => 'Fatty',
    age => 8,
    diet => 'Sea Treats'
);

say $fat->name, ' eats ', $fat->diet;

$fat->diet('Low Sodium Kitty Lo Mein');
say $fat->name, ' now eats ', $fat->diet;

При попытке изменить ro-атрибут будет выброшено исключение.

Некоторые разработчики предпочитают делать все атрибуты только для чтения и передавать начальные значения через конструктор — это повышает надёжность кода.

Таким образом, объект содержит связанные данные и может выполнять над ними действия. Класс описывает эти данные и поведения. Разные экземпляры имеют своё состояние, но используют один и тот же интерфейс методов.

Инкапсуляция

Moose позволяет описывать атрибуты экземпляров классов, а также управлять их свойствами (например, имя кота нельзя изменить после задания). Само Moose решает, как хранить эти данные — доступ к ним осуществляется через аксессоры. Это и есть инкапсуляция: скрытие деталей реализации от пользователей объекта.

Пример расчёта возраста кота на основе года рождения:

package Cat {
    use Moose;
    has 'name', is => 'ro', isa => 'Str';
    has 'diet', is => 'rw';
    has 'birth_year', is => 'ro', isa => 'Int';

    sub age {
        my $self = shift;
        my $year = (localtime)[5] + 1900;
        return $year - $self->birth_year;
    }
}

Синтаксис создания объектов изменился, но использование объекта снаружи осталось прежним. Это и есть суть инкапсуляции.

Совместимость и API

Вы можете настроить конструктор Moose так, чтобы принимать возраст и вычислять birth_year автоматически. Подробнее — в Moose::Manual::Attributes.

Пример с атрибутом по умолчанию:

package Cat {
    use Moose;
    has 'name', is => 'ro', isa => 'Str';
    has 'diet', is => 'rw', isa => 'Str';
    has 'birth_year',
        is => 'ro',
        isa => 'Int',
        default => sub { (localtime)[5] + 1900 };
}

Создание объекта без указания года рождения:

my $kitten = Cat->new( name => 'Hugo' );

Полиморфизм

Главная сила ООП — это возможность работы с разными типами данных через общий интерфейс.

sub show_vital_stats {
    my $object = shift;
    say 'My name is ', $object->name;
    say 'I am ', $object->age;
    say 'I eat ', $object->diet;
}

Функция show_vital_stats работает с любым объектом, который поддерживает методы name(), age() и diet(). Это и есть полиморфизм — возможность заменить один объект на другой, если интерфейс совпадает.

Duck Typing

Perl не требует формального объявления отношений между классами. Если объект умеет quack(), его можно считать уткой — это и есть "утиная типизация" (duck typing).

Пример использования методов с разным смыслом в зависимости от контекста:

# возраст кота
my $years = $zeppie->age;

# выдержка сыра
$cheese->age;

Таким образом, важно не только наличие методов, но и то, что они на самом деле делают.

Роли

Роль — это именованная коллекция поведения и состояния. Класс организует поведение и состояние для объектов, а роль группирует их в именованные коллекции. Роль нельзя инстанцировать напрямую, её можно только "исполнить" в классе.

Например, Animal может выполнять роль LivingBeing, а Cheese — роль Storable:

package LivingBeing {
    use Moose::Role;
    requires qw( name age diet );
}

Класс Cat должен явно указать, что он реализует эту роль:

package Cat {
    use Moose;
    has 'name', is => 'ro', isa => 'Str';
    has 'diet', is => 'rw', isa => 'Str';
    has 'birth_year', is => 'ro', isa => 'Int', default => sub { (localtime)[5] + 1900 };
    with 'LivingBeing';
    sub age {
        my $self = shift;
        my $year = (localtime)[5] + 1900;
        return $year - $self->birth_year;
    }
}

Теперь можно проверить поддержку роли через метод DOES:

say 'Alive!' if $fluffy->DOES('LivingBeing');
say 'Moldy!' if $cheese->DOES('LivingBeing');

Роли позволяют разделять поведение и реализацию. Например, можно вынести расчёт возраста в отдельную роль:

package CalculateAge::From::BirthYear {
    use Moose::Role;
    has 'birth_year', is => 'ro', isa => 'Int', default => sub { (localtime)[5] + 1900 };

    sub age {
        my $self = shift;
        my $year = (localtime)[5] + 1900;
        return $year - $self->birth_year;
    }
}

И затем применить сразу несколько ролей:

package Cat {
    use Moose;
    has 'name', is => 'ro', isa => 'Str';
    has 'diet', is => 'rw';
    with 'LivingBeing', 'CalculateAge::From::BirthYear';
}

Наследование

Перл поддерживает наследование: дочерний класс расширяет поведение родительского класса, добавляя новое или переопределяя старое. Наследование — это частный случай выполнения роли.

Когда использовать роли, а когда наследование?

  • Наследование — если класс действительно расширяет родительский.
  • Роли — если класс требует дополнительного поведения, особенно если его можно осмысленно назвать.

Пример базового класса LightSource:

package LightSource {
    use Moose;

    has 'candle_power', is => 'ro', isa => 'Int', default => 1;
    has 'enabled', is => 'ro', isa => 'Bool', default => 0, writer => '_set_enabled';

    sub light {
        my $self = shift;
        $self->_set_enabled(1);
    }

    sub extinguish {
        my $self = shift;
        $self->_set_enabled(0);
    }
}

Атрибут enabled имеет приватный аксессор _set_enabled, который используется внутри методов.

Наследование и атрибуты

Подкласс LightSource может определить промышленную супер-свечу с яркостью в сто раз больше:

package SuperCandle {
    use Moose;
    extends 'LightSource';
    has '+candle_power', default => 100;
}

extends принимает список имён классов-родителей. Если бы в классе была только эта строка, объекты SuperCandle вели бы себя как LightSource. У экземпляра SuperCandle были бы атрибуты candle_power и enabled и методы light() и extinguish().

Плюс + перед именем атрибута (например, candle_power) указывает, что класс переопределяет атрибут. Здесь новое значение по умолчанию — 100.

Порядок вызова методов (MRO)

Перл сначала ищет метод в классе объекта, затем у родителя, потом у предков и так далее. При множественном наследовании (например, Hovercraft от Boat и Car) порядок поиска становится сложнее. Перл использует стратегию поиска в глубину, но модуль mro позволяет изменить это поведение на, например, C3.

Наследование и методы

Как и атрибуты, методы могут быть переопределены:

package Glowstick {
    use Moose;
    extends 'LightSource';
    sub extinguish {}
}

Вызов extinguish() на объекте Glowstick ничего не делает. Чтобы явно показать намерение переопределить метод, в Moose используют override и super():

package LightSource::Cranky {
    use Carp 'carp';
    use Moose;
    extends 'LightSource';
    
    override light => sub {
        my $self = shift;
        carp "Can't light a lit LightSource!" if $self->enabled;
        super();
    };
    
    override extinguish => sub {
        my $self = shift;
        carp "Can't extinguish unlit LightSource!" unless $self->enabled;
        super();
    };
}

Наследование и isa()

Метод isa() возвращает истину, если объект является экземпляром или потомком указанного класса:

say 'Похоже на LightSource' if $sconce->isa('LightSource');
say 'Hominidae не светятся' unless $chimpy->isa('LightSource');

Moose и объектная система Perl

Moose расширяет стандартные возможности Perl для ООП, предоставляя конструкторы, деструкторы, аксессоры и инкапсуляцию. При этом можно работать и с обычными объектами Perl.

Пример использования метаобъектного протокола:

my $metaclass = Monkey::Pants->meta;
say 'Атрибуты Monkey::Pants:';
say $_->name for $metaclass->get_all_attributes;
say 'Методы Monkey::Pants:';
say $_->fully_qualified_name for $metaclass->get_all_methods;

Можно увидеть и подклассы:

my $metaclass = Monkey->meta;
say 'Monkey — родитель классов:';
say $_ for $metaclass->subclasses;

MooseX::Declare и Moops

MooseX::Declare добавляет ключевые слова class, role и method:

use MooseX::Declare;

role LivingBeing { requires qw( name age diet ) }

role CalculateAge::From::BirthYear {
    has 'birth_year',
        is => 'ro',
        isa => 'Int',
        default => sub { (localtime)[5] + 1900 };
    
    method age {
        return (localtime)[5] + 1900 - $self->birth_year;
    }
}

class Cat with LivingBeing with CalculateAge::From::BirthYear {
    has 'name', is => 'ro', isa => 'Str';
    has 'diet', is => 'rw';
}

Аналогичный код на Moops:

use Moops;

role LivingBeing {
    requires qw( name age diet );
}

role CalculateAge::From::BirthYear :ro {
    has 'birth_year',
        isa => Int,
        default => sub { (localtime)[5] + 1900 };
    
    method age {
        return (localtime)[5] + 1900 - $self->birth_year;
    }
}

class Cat with LivingBeing with CalculateAge::From::BirthYear :ro {
    has 'name', isa => Str;
    has 'diet', is => 'rw';
}

Стройные Лоси (The Svelte Alces)

Moose — не маленькая библиотека, но очень мощная. Популярной альтернативой является Moo — более лёгкая библиотека, почти полностью совместимая с Moose. При необходимости экономии памяти или скорости многие проекты частично или полностью переходят на Moo. Начинайте с Moose, а затем оценивайте целесообразность перехода.

Blessed-ссылки

Базовая объектная система Perl минималистична и опирается на три правила:

  • Класс — это пакет.
  • Метод — это функция.
  • Объект — это благословленная ссылка.

Из этих правил можно построить любую объектную систему. Хотя минимализм затрудняет метапрограммирование, для небольших программ он подходит. Для проектов больше нескольких сотен строк лучше использовать Moose.

bless связывает ссылку с именем класса, превращая её в объект:


sub new {
my $class = shift;
bless {}, $class;
}

Конструктор обычно называется new() и принимает имя класса как первый аргумент. Можно использовать разные типы ссылок:


my $array_obj = bless [], $class;
my $scalar_obj = bless \$scalar, $class;
my $func_obj = bless \&some_func, $class;

Пример класса для баскетболистов:


package Player {
sub new {
my ($class, %attrs) = @_;
bless \%attrs, $class;
}
}

Создание объектов:


my $joel = Player->new( number => 10, position => 'center' );
my $damian = Player->new( number => 0, position => 'guard' );

Доступ к данным напрямую небезопасен:


sub format {
my $self = shift;
return '#' . $self->{number} . ' plays ' . $self->{position};
}

Лучше использовать аксессоры:


sub number { return shift->{number} }
sub position { return shift->{position} }

Поиск методов и наследование

При вызове метода Perl ищет его сначала в классе объекта, затем у родителей:


my $number = $joel->number;

Чистота пространств имён

Модуль namespace::autoclean помогает избегать нежелательных коллизий между импортированными функциями и методами.

Перл хранит родительские классы в массиве @ISA:


package InjuredPlayer {
@InjuredPlayer::ISA = 'Player';
}

Чище использовать pragma parent:


package InjuredPlayer {
use parent 'Player';
}

Перл поддерживает множественное наследование:


package InjuredPlayer; {
use parent qw( Player Hospital::Patient );
}

AUTOLOAD

Если метод не найден, Perl ищет функцию AUTOLOAD() в классах по порядку разрешения методов. При множественном наследовании это усложняет понимание кода.

Переопределение методов и SUPER

В Perl можно переопределить метод родительского класса, объявив одноимённый метод в потомке:


sub overridden {
my $self = shift;
warn 'Called overridden() in child!';
return $self->SUPER::overridden( @_ );
}

SUPER:: указывает Perl искать метод у родителя. Будьте осторожны: SUPER:: может неправильно работать при импорте методов из других пакетов. Модуль SUPER на CPAN решает эту проблему.

Moose использует свой super(), который лишён этих недостатков.

Стратегии работы с благословленными ссылками

Благословленные ссылки могут казаться одновременно минималистичными и запутанными. Moose делает работу с объектами проще. Но если приходится работать с кодом на чистом Perl, вот несколько рекомендаций:

  • Не смешивайте функции и методы в одном классе.
  • Для каждого класса используйте отдельный .pm-файл.
  • Соблюдайте стандартные соглашения: конструктор new(), имя переменной $self и т.д.
  • Используйте аксессоры повсеместно (например, через Class::Accessor).
  • Избегайте AUTOLOAD(), а если используете — объявляйте функции заранее.
  • Пишите классы так, чтобы их было легко расширить или делегировать.
  • Используйте вспомогательные модули вроде Role::Tiny для переиспользования кода.

Рефлексия

Рефлексия (инспекция) — это возможность программы анализировать саму себя во время выполнения. Moose через Class::MOP значительно упрощает задачи рефлексии.

Проверка загрузки модуля

Чтобы проверить, загружен ли модуль, смотрим в хэш %INC:


sub module_loaded {
(my $modname = shift) =~ s!::!/!g;
return exists $INC{ $modname . '.pm' };
}

Или используйте is_class_loaded() из модуля Class::Load.

Проверка существования пакета

Пакет существует, если можно вызвать can() у него:


say "$pkg существует" if eval { $pkg->can('can') };

Проверка версии модуля

Почти все модули наследуют метод VERSION() из UNIVERSAL:


my $version = $module->VERSION;

Проверка существования функции

Проверяем через can():


say "$func() существует" if $pkg->can($func);

Если есть сомнения, оберните вызов в eval. Осторожно с функциями через AUTOLOAD() — они могут давать неправильные результаты.

Проверка существования метода

Чёткой разницы между функцией и методом Perl не делает, но can() — лучший способ.

Работа с таблицами символов

Таблицы символов в Perl — это хэши, содержащие все глобальные переменные пакета. Например:


%MonkeyGrinder::

Модуль Package::Stash упрощает безопасную работу с таблицами символов.

Продвинутое ООП в Perl

Предпочитайте композицию наследованию

Новички в проектировании ООП часто чрезмерно используют наследование для повторного использования кода и для использования полиморфизма. В результате получается глубокая иерархия классов с разбросанными повсюду обязанностями. Поддерживать такой код сложно — кто знает, где нужно добавить или изменить поведение? Что произойдет, если код в одном месте конфликтует с кодом, объявленным в другом месте? Наследование — это всего лишь один из многих инструментов для программистов ООП. Это не всегда правильный инструмент. Это часто неправильный инструмент. Например, автомобиль (Car) может расширять Vehicle::Wheeled (отношение “is-a” — “является”), но лучше, если Car будет содержать несколько объектов Wheel в виде атрибутов экземпляра (отношение “has-a” — “имеет”). Разбиение сложных классов на более мелкие, сфокусированные сущности улучшает инкапсуляцию и снижает вероятность того, что какой-то один класс или роль будут делать слишком много. Меньшие, более простые и лучше инкапсулированные сущности легче понимать, тестировать и поддерживать.

Принцип единственной ответственности

Когда вы проектируете свою объектную систему, учитывайте обязанности каждой сущности. Например, объект Employee может представлять конкретную информацию о личных данных человека — его имени, контактной информации и другой личной информации, тогда как объект Job может представлять бизнес-обязанности. Разделение этих сущностей по их обязанностям позволяет классу Employee сосредоточиться только на управлении информацией о человеке, а классу Job — представлять, чем человек занимается. (Например, два Employee могут совместно выполнять одну Job, или один Employee может иметь одновременно должности CFO и COO.) Когда каждый класс имеет только одну ответственность, вы уменьшаете связанность между классами и улучшаете инкапсуляцию данных и поведения, специфичных для класса.

Принцип DRY (Don't Repeat Yourself)

Сложность и дублирование усложняют разработку и сопровождение. Принцип DRY (Don’t Repeat Yourself — “Не повторяй себя”) напоминает о необходимости искать и устранять дублирование в системе. Дублирование существует как в данных, так и в коде. Вместо повторения конфигурационной информации, пользовательских данных и других важных артефактов вашей системы создавайте одну единственную каноническую репрезентацию этой информации, из которой можно будет генерировать другие представления. Этот принцип помогает вам найти оптимальное представление вашей системы и данных и снижает вероятность расхождения дублированной информации.

Принцип подстановки Лисков

Принцип подстановки Лисков гласит, что вы должны иметь возможность заменить специализацию класса или роли на оригинал без нарушения API оригинала. Иными словами, объект должен быть таким же общим в ожиданиях и как минимум столь же специфичным в выдаче результатов, как объект, который он заменяет. Представьте два класса: Dessert и его дочерний класс PecanPie. Если классы следуют принципу подстановки Лисков, вы можете заменить каждый объект Dessert объектом PecanPie в тестах, и всё должно успешно работать. См. статью Рэга Брейтуэйта “IS-STRICTLY-EQUIVALENT-TO-A” для получения дополнительных подробностей.

Подтипы и преобразования

Moose позволяет объявлять и использовать типы, а также расширять их через подтипы для всё более специализированного описания того, что представляют ваши данные и как они себя ведут. Эти аннотации типов помогают проверять правильность параметров функций и методов — или автоматически приводить их к правильным типам. Например, вы можете захотеть позволить пользователям указывать дату для записи в Ledger в виде строки, а внутри представлять её как экземпляр DateTime. Это можно сделать, создав тип Date и добавив преобразование из строки. См. Moose::Util::TypeConstraints и MooseX::Types для получения дополнительных сведений.

Иммутабельность объектов

При хорошо спроектированном объекте вы говорите ему, что делать, а не как это делать. Если вы обнаруживаете, что обращаетесь к данным экземпляра объекта (даже через аксессоры) вне самого объекта, это значит, что у вас слишком много доступа к внутренностям объекта. Новички в ООП часто воспринимают объекты как наборы записей, использующих методы для получения и установки внутренних значений. Эта простая техника ведет к соблазну размыть обязанности объекта по всей системе. Вы можете предотвратить неправильный доступ, сделав свои объекты иммутабельными. Передавайте все необходимые данные через конструктор, затем запрещайте любые изменения этой информации извне класса. Не предоставляйте методов для изменения внутренних данных — сделайте все публичные аксессоры только для чтения и используйте внутренние writers крайне осторожно. После создания такого объекта вы будете уверены, что он всегда находится в валидном состоянии. Его данные нельзя будет изменить так, чтобы привести его в некорректное состояние. Это требует огромной дисциплины, но в результате создаются надёжные, тестируемые и поддерживаемые системы. Некоторые проекты заходят так далеко, что запрещают даже изменение данных экземпляра внутри самого класса.

Итог — надёжные, тестируемые и легко поддерживаемые системы.
